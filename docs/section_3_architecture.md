# Раздел 3. Архитектура

**Версия:** 0.1 (draft под защиту)
**Дата:** 2026-05

---

## 3.1. Общая схема

Архитектура реализует принципы П1–П5 (см. раздел 2) как последовательность из четырёх специализированных компонентов. Каждый компонент решает функционально замкнутую подзадачу и может быть заменён или перенастроен независимо от остальных.

```
                  ┌──────────────────────────┐
   Image  ──────► │  BLIP-large              │ ──► caption_en
                  │  Salesforce/blip-large   │
                  └──────────────────────────┘
                              │
                              ▼
                  ┌──────────────────────────┐
                  │  MarianMT (EN → RU)      │ ──► caption_ru
                  │  Helsinki-NLP/opus-mt    │
                  └──────────────────────────┘
                              │
   Image  ──────► ┌──────────────────────────┐
                  │  SigLIP zero-shot        │ ──► metadata =
                  │  google/siglip-base      │     {image_type, style,
                  │  4 закрытые таксономии   │      theme, mood, tags}
                  └──────────────────────────┘
                              │
                              ▼
                  ┌──────────────────────────┐
                  │  DescriptionBuilder      │ ──► archive_description_ru,
                  │  template_mode           │     search_text
                  └──────────────────────────┘
```

Архитектура поддерживает **два режима работы** (см. п. 3.6), переключаемых параметром `template_mode` в компоненте сборки. Все остальные компоненты — общие для обоих режимов.

В таблице ниже приведены конечные численные характеристики архитектуры; обоснования по каждому компоненту даются в пп. 3.2–3.5.

| Компонент | Модель | Параметров | Размер | Latency, CPU |
|---|---|---|---|---|
| Captioning | `Salesforce/blip-image-captioning-large` | 470M | 990 MB | 0.6 s/img |
| Translation | `Helsinki-NLP/opus-mt-en-ru` | 76M | 300 MB | 0.1 s/cap |
| Semantic | `google/siglip-base-patch16-224` | 200M | 800 MB | 0.4 s/img |
| Assembly | детерминированный шаблон | — | — | < 1 ms |
| **Итого** | | **≈ 750M** | **≈ 2.1 GB** | **≈ 1.1 s/img** |

## 3.2. Компонент визуального распознавания: BLIP-large

### Назначение

Извлечение содержательного описания изображения на промежуточном языке (английский). Выбор английского как промежуточного обусловлен принципиально более широкой доступностью предобученных моделей captioning для пары «изображение → английский текст» по сравнению с парой «изображение → русский текст».

### Выбор модели

В качестве captioning-модели выбран **BLIP-large** (`Salesforce/blip-image-captioning-large`) — предобученная модель на корпусе COCO + Visual Genome + Conceptual Captions + SBU. Сравнение с BLIP-base (`Salesforce/blip-image-captioning-base`) проведено в эксперименте E-1 (см. раздел 4) на полной решётке `template_mode`:

| Backbone | template_mode | CLIPScore_RU | R@1 | R@10 |
|---|---|---|---|---|
| BLIP-base | full −theme −mood | 0.287 | 0.14 | 0.54 |
| BLIP-base | caption_only | 0.254 | 0.15 | 0.57 |
| **BLIP-large** | full −theme −mood | **0.298** | 0.24 | 0.61 |
| **BLIP-large** | caption_only | 0.274 | **0.27** | **0.63** |

BLIP-large превосходит BLIP-base **на всех четырёх режимах шаблона** по обеим целевым метрикам (+0.5–1% CLIPScore, +5–7% R@1, p<0.001 paired bootstrap).

### Параметры генерации

Используется детерминированная декодировка (`do_sample=False`, `num_beams=1`, `max_new_tokens=50`). Эксперимент E-5+6 по перебору параметров декодирования (beam search, length penalty, prompt prefix) включён в раздел 4 как ablation; в случае значимого улучшения параметры будут обновлены в финальной версии архитектуры.

## 3.3. Компонент перевода: MarianMT

### Назначение

Перевод полученного на предыдущем шаге англоязычного caption на русский язык. Получаемый русскоязычный текст служит входом для компонента сборки.

### Выбор модели

В качестве translator выбран **MarianMT** в варианте `Helsinki-NLP/opus-mt-en-ru` — специализированная модель для пары английский→русский, обученная на корпусе OPUS (OpenSubtitles, Wikipedia, news, web). Обоснование выбора опирается на **три независимых соображения**.

#### Соображение A — эмпирическое (главное)

В эксперименте E-9 (см. раздел 4) проведено прямое сравнение MarianMT и более крупной мультилингвальной модели NLLB-200-distilled-600M на полном пуле n=220:

| Translator | Параметров | CLIPScore_RU | R@1 | R@10 |
|---|---|---|---|---|
| MarianMT (opus-mt-en-ru) | 76M | 0.288 | 0.21 | 0.49 |
| NLLB-200-distilled-600M | 615M | 0.287 | 0.21 | 0.48 |

Paired bootstrap p ≈ 0.7 — статистически значимой разницы между моделями нет. Это позволяет утверждать, что **перевод не является узким местом пайплайна**: качественный апгрейд translator'a не приводит к улучшению ни достоверности, ни поисковости итоговых описаний.

#### Соображение B — операционное

При эквивалентном качестве на целевой задаче MarianMT обеспечивает существенные операционные преимущества:

| Параметр | MarianMT | NLLB-200-600M |
|---|---|---|
| Параметров | 76M | 615M |
| Размер на диске | 300 MB | 2.4 GB |
| Latency на CPU | 0.1 s/caption | 0.3 s/caption |
| On-prem развёртывание | да | да |
| Зависимость от внешних API | нет | нет |

Преимущества важны в контексте архивной инфраструктуры заказчика: (1) on-prem развёртывание исключает передачу данных каталога за пределы периметра библиотеки; (2) меньшее потребление ресурсов критично при массовой обработке коллекции (десятки тысяч открыток); (3) фиксированные веса обеспечивают воспроизводимость, недоступную при использовании коммерческих SaaS-переводчиков.

#### Соображение C — доменное

Входом translator'a служат короткие descriptive captions, порождённые BLIP-large: нейтральный английский, ≤50 токенов, без специализированной историко-культурной лексики. Этот режим попадает в **core distribution обучающих данных MarianMT**. Историко-культурные термины, в которых более крупные мультилингвальные модели потенциально могли бы давать выигрыш, в captions от BLIP не встречаются — они появлялись бы только при ручном описании, что не является режимом работы пайплайна.

### Итоговая формулировка обоснования

MarianMT выбран как компонент перевода по совокупности трёх соображений: (A) эмпирическое сравнение с NLLB-200-distilled-600M в эксперименте E-9 показало отсутствие значимой разницы в целевых метриках; (B) при равном качестве MarianMT в 8 раз меньше и в 3 раза быстрее, что делает его предпочтительным для on-prem развёртывания; (C) короткие descriptive captions, поступающие на вход, попадают в core distribution обучающих данных MarianMT, что делает выигрыш более крупных мультилингвальных моделей маловероятным.

## 3.4. Компонент семантического обогащения: SigLIP zero-shot

### Назначение

Атрибуция изображения по фиксированным таксономиям, релевантным архивному поиску. Реализует принцип П2 (закрытые таксономии вместо свободной генерации).

### Выбор модели

В качестве классификатора выбран **SigLIP** в варианте `google/siglip-base-patch16-224` — мультимодальный энкодер с sigmoid-loss training, демонстрирующий устойчивое преимущество над CLIP в zero-shot режиме на сценах с тонкими визуальными различиями. SigLIP применяется без дополнительного обучения: каждая метка таксономии формулируется как короткий английский текстовый шаблон, и вычисляется косинусное сходство между эмбеддингом изображения и эмбеддингом каждого шаблона.

### Таксономии

В системе используются **четыре закрытые таксономии**, специфицированные совместно с предметной областью:

| Таксономия | Метки | Назначение |
|---|---|---|
| `image_type` | postcard, poster, greeting card, illustration, photograph | Тип архивного материала |
| `style` | vintage illustration, retro design, decorative illustration, engraving, drawing, painting, black and white photo, color photograph | Художественная техника |
| `theme` | holiday / Easter / Christmas / New Year / romantic / children / urban / nature / religious scene | Тематическая категория |
| `mood` | happy, festive, romantic, nostalgic, calm, serious | Эмоциональный тон |

### Калибровка порогов уверенности

Для каждой таксономии задан порог уверенности: метка попадает в итоговое описание только при превышении порога. Текущие значения порогов (image_type=0.35, style=0.22, theme=0.18, mood=0.18) подобраны эвристически. Эксперимент E-13 (см. раздел 4) посвящён их калибровке через ручную разметку 50 примеров; калиброванные пороги — потенциальный источник дальнейшего улучшения.

### Замечание о пути перевода меток

Перевод меток таксономии на русский язык выполняется через детерминированные словари в компоненте сборки (п. 3.5), а не через машинный перевод. Это решение принципиально: словарь архивных таксономий — конечный, фиксированный и согласованный с действующими каталожными классификаторами библиотеки; машинный перевод вносил бы вариабельность, разрушающую совместимость с фасетным поиском.

## 3.5. Компонент сборки описания: DescriptionBuilder

### Назначение

Построение итогового русскоязычного описания из caption_ru и метаданных таксономии по контролируемому шаблону. Реализует управляемую гибридную генерацию (см. раздел 2, п. 2.4): свободная часть текста — caption — отражает визуальную конкретику, контролируемая — таксономические атрибуты — обеспечивает архивную стандартизацию.

### Режимы шаблона

DescriptionBuilder поддерживает три режима, выбираемые параметром `template_mode`:

**Режим `full`** — полное описание с типом, стилем, caption, темой и настроением:
> *Открытка в стиле винтажная иллюстрация. На изображении: рождественский ангел с букетом цветов. Предположительно, это рождественская сцена. Общее настроение изображения можно охарактеризовать как праздничное.*

**Режим `full −theme −mood`** (вариант `full` с отключёнными темой и настроением) — описание без оценочных полей:
> *Открытка в стиле винтажная иллюстрация. На изображении: рождественский ангел с букетом цветов.*

**Режим `minimal`** — только caption в шаблонной обёртке:
> *На изображении: рождественский ангел с букетом цветов.*

**Режим `caption_only`** — необработанный caption_ru без шаблонной обёртки:
> *рождественский ангел с букетом цветов.*

Помимо основного описания, компонент дополнительно порождает **`search_text`** — конкатенацию таксономических меток, не зависящую от выбранного режима. `search_text` используется для индексации в поисковой системе и не предъявляется пользователю.

### Обоснование наличия нескольких режимов

Выбор режима не сводится к технической настройке: он определяет рабочую точку на trade-off между достоверностью и поисковостью (принцип П4). Эмпирические основания и формулировка двух эксплуатационных конфигураций приведены в п. 3.6.

## 3.6. Два эксплуатационных режима

Согласно П4, метод не пытается устранить trade-off между достоверностью описаний (`CLIPScore_RU`) и их различимостью при retrieval (`Recall@k`), а делает его явным параметром эксплуатации. На основе эксперимента 2 × 4 (см. раздел 4) зафиксированы **две рекомендуемые конфигурации**.

| Параметр | Retrieval-режим | Display-режим |
|---|---|---|
| `template_mode` | `caption_only` | `full −theme −mood` |
| `CLIPScore_RU` | 0.274 | **0.298** |
| `R@1` | **0.27** | 0.24 |
| `R@10` | **0.63** | 0.61 |
| Целевой use case | поисковый индекс НЭБ | карточка документа |
| Оптимизируемое качество | различимость описаний | информативность и достоверность |

### Retrieval-режим

Используется как источник текстового представления открытки для индексации в поисковой системе. Минимизация шаблонной части (только caption_ru без обвеса) обеспечивает максимальную различимость описаний между открытками, что напрямую отражается в Recall@k. Tax-таксономические метки, не входящие в основное описание, по-прежнему доступны через поле `search_text`, индексируемое параллельно.

### Display-режим

Используется при отображении карточки документа в каталоге. Включает тип материала и художественный стиль (поля theme и mood намеренно отключены: эксперимент E-16 показал, что их низкая надёжность приводит к стилистическому шуму и потере CLIPScore). Полученное описание ближе к каталожному стандарту и обеспечивает максимальное alignment с изображением по CLIPScore.

### Замечание о выборе между режимами

Решение о работе в одном или обоих режимах — за заказчиком (РГБ). Технически архитектура допускает их параллельную работу: один прогон пайплайна порождает оба варианта описания (компонент сборки переключается параметром, остальные компоненты — общие).

## 3.7. Сценарий развёртывания у заказчика

Архитектура спроектирована с учётом операционных требований архивной инфраструктуры:

**Аппаратные требования.** Минимальная конфигурация — одна машина без GPU, 16 GB RAM, ≈3 GB дискового пространства под веса моделей. Пропускная способность — ≈1 открытка/с на одном CPU-ядре. При параллельной обработке (8 ядер) — ≈8 открыток/с, ≈30 000 открыток/час. Полная коллекция открыток РГБ (порядка сотен тысяч единиц) обрабатывается за день.

**Развёртывание.** Все веса моделей находятся в open-source репозиториях Hugging Face и загружаются один раз; работа пайплайна не требует обращения к внешним API в режиме исполнения. Это удовлетворяет требованию о замкнутости периметра обработки.

**Интеграция.** Пайплайн порождает два поля для каждой открытки: `archive_description` (отображаемый текст карточки) и `search_text` (служебная строка для индексации). Оба поля прозрачно интегрируются в существующую структуру записи НЭБ/РГБ.

**Сопровождение.** Замена любого компонента (например, переход на новый translator или новый captioning backbone) не требует переобучения остальных. Калибровка SigLIP-порогов (см. эксперимент E-13) выполняется на 50 размеченных примерах и не требует полного релиза.

## 3.8. Резюме раздела

Архитектура состоит из четырёх специализированных компонентов: BLIP-large для визуального распознавания, MarianMT для перевода, SigLIP для классификации по четырём закрытым таксономиям и детерминированный DescriptionBuilder для сборки итогового текста. Выбор каждого компонента обоснован эмпирически (BLIP-large vs BLIP-base — E-1; MarianMT vs NLLB-200 — E-9), операционно (on-prem развёртываемость, latency, размер) и доменно (соответствие архивным стандартам через закрытые таксономии).

Архитектура поддерживает два эксплуатационных режима: retrieval-режим (`caption_only`) — для интеграции с поисковой системой, и display-режим (`full −theme −mood`) — для отображения в каталоге. Выбор режима — явный параметр эксплуатации, отражающий главный методологический результат работы — trade-off между достоверностью и поисковостью.

Полное эмпирическое обоснование архитектурных выборов приведено в разделе 4.
